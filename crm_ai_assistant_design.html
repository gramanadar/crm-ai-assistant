Internal Document & CRM Assistant

An assistant that answers questions from company documents with source references, classifies incoming support requests, looks up CRM records, and prepares CRM updates that a person approves before anything is written.

Python · FastAPIRAG with citationsValidated structured outputsHuman approval for writesNo invented results

1. Summary

The goal is to cut manual document searches and repetitive CRM data entry without letting the AI take an action, or state a fact, that nobody can check.

The system has four capabilities on one FastAPI backend: a knowledge assistant that answers from up to ten supplied documents and cites its sources; a classifier that sorts requests into up to five agreed categories and sends unclear ones to a person; an agent that can look up CRM records through a read-only tool and draft CRM notes or tasks; and an n8n workflow that routes requests, notifies the team and triggers approved CRM updates.

Key safety decision: the language model can read the CRM but can never write to it. It produces a draft; a person approves it; the backend performs the write with validation and duplicate protection. The write endpoint is never exposed to the model as a tool.

3. Design principles

Evidence or silence

The assistant only states what a retrieved document or a successful CRM lookup supports. Otherwise it says it doesn't know.

Validate everything the model returns

All model output is parsed against a schema. Invalid output is never passed on; it's retried once, then routed to a person.

Humans own consequential actions

Reads are automated; writes need approval. Approval is recorded with who, when and exactly what was approved.

Failures are visible states

Timeouts, errors and partial results appear as explicit statuses in the API, UI and logs, never as a plausible-looking answer.

Measured, not asserted

Quality claims come from evaluation sets that can be rerun after every change.

Small and boring

One database (PostgreSQL with pgvector) for vectors, records, idempotency and audit. No extra infrastructure the client must run.

4.1 Why one backend owns the CRM write

n8n triggers approved updates but doesn't call the CRM write endpoint directly. It calls the backend, which enforces validation, idempotency and audit in one place. This keeps the duplicate-prevention guarantee true however an action is triggered (UI button, n8n, a retry).

5. RAG knowledge assistant

5.1 Ingestion

  1. Accept text-based PDF (PyMuPDF) and DOCX (python-docx). Record file name, SHA-256 checksum, version and upload time. Re-uploading an unchanged file is a no-op.
  2. Extract text with structure: headings, page numbers (PDF), paragraph order, tables converted to readable rows.
  3. Detect pages with little or no extractable text and report them as warnings. OCR is out of scope, so scanned pages are flagged, not silently skipped.
  4. Produce an ingestion report per document: pages, characters, chunks created, warnings.

5.2 Chunking

  • Structure-aware: split on headings first, then paragraphs, so a chunk rarely mixes unrelated topics.
  • Target size about 500–800 tokens with roughly 10–15% overlap, tuned on the retrieval eval rather than fixed up front.
  • Metadata on every chunk: document ID, title, section heading path, page range, chunk index. The heading path is also prepended to the chunk text before embedding, which noticeably improves retrieval on short chunks.

5.3 Embeddings and vector store

  • Vector DB: PostgreSQL with pgvector (HNSW index, cosine distance). With ten documents this is small; one database also holds requests, drafts and audit data.
  • Embeddings: a hosted embedding model (e.g. OpenAI text-embedding-3-small or Voyage AI). Anthropic doesn't offer an embedding model, so this is chosen separately from the answer model. The model name is stored with each vector so a later change triggers re-embedding, not mixed vectors.
  • Hybrid retrieval: combine vector similarity with PostgreSQL full-text search (reciprocal rank fusion). Keyword search catches exact terms such as product codes and policy numbers that embeddings often miss.
  • Retrieve the top 8 candidates and pass those above a similarity floor to the model.

5.4 Answer generation

The model receives the question and the retrieved chunks, each labelled with its chunk ID, and must return this validated structure:

{
  "status": "answered" | "partial" | "not_found",
  "answer": "string (empty when not_found)",
  "claims": [
    {"text": "statement in the answer", "chunk_ids": ["c_0412", "c_0413"]}
  ],
  "missing_information": "what the documents don't cover (for partial / not_found)"
}

The system prompt tells the model to answer only from the supplied chunks, to treat chunk content as data rather than instructions, and to choose not_found rather than guess.

5.5 Citation and missing-information checks (backend, not model)

  • Every cited chunk_id must be in the retrieved set. A citation to anything else is treated as a fabricated citation: the answer is rejected and regenerated once, then returned as not_found with an error logged.
  • An answered status with no claims is downgraded to not_found.
  • If no chunk passes the similarity floor, the model isn't called; the API returns not_found directly. That's cheaper and can't hallucinate.
  • The UI renders citations as document title, section and page, with the source passage on hover.
Note on Claude's native citations: Claude can return citations natively when documents are passed as document blocks, but that feature can't be combined with structured output formats. This design uses chunk-ID citations in the structured response so it behaves the same on Claude and OpenAI and can be validated by the backend.

6. Request classification

6.1 Output contract

{
  "category": "billing" | "technical" | "account" | "sales" | "other",   // the 5 agreed labels
  "confidence": 0.0 - 1.0,
  "is_ambiguous": true | false,
  "reason": "one sentence, for the reviewer",
  "extracted": {"customer_email": "...", "order_id": "..."}             // optional fields for CRM mapping
}

Labels above are placeholders until the client confirms the five categories. The schema is enforced through the provider's structured output feature and then validated again with Pydantic. Category values are an enum, so the model can't invent a sixth label.

6.2 Prompt design

  • Each category gets a definition, two or three examples, and explicit boundary rules ("a refund request about a failed payment is billing, not technical").
  • Examples come from the client's labeled data, held separate from the test split so the evaluation stays honest.
  • The request text is wrapped and marked as untrusted content, so instructions inside a request ("ignore previous rules") are classified, not obeyed.

6.3 Routing to human review

A request goes to the review queue if any of these hold:

  • Output fails schema validation after one retry.
  • is_ambiguous is true, or the category is other.
  • confidence is below a threshold chosen on the evaluation set (§16.2).
  • Optional consistency check: classify twice; disagreement means review.
Honest note on confidence: a model's self-reported confidence is only loosely calibrated. The threshold is therefore chosen from measured results (accuracy against review rate on the labeled set), not assumed. The client chooses the trade-off between automation and safety.

Reviewers can confirm or correct the category in the UI. Corrections are stored and can become new labeled examples later.

7. Agent and CRM integration

7.1 Tools exposed to the model

ToolTypePurpose
search_documentsReadSame retrieval as §5, so the agent can combine document and CRM answers
crm_lookupReadCalls the single read-only CRM endpoint (e.g. find contact or case by email or ID)
draft_crm_actionLocal onlyCreates a draft note or task in the database. Doesn't contact the CRM

Tool schemas are strict (no extra properties, required fields listed), and inputs are validated again in the backend before anything runs. The agent loop has a hard limit on tool calls per request (e.g. 5) and an overall time budget.

7.2 Orchestration

A small explicit loop in the backend: send the conversation and tools, run requested tools, return the results, repeat until the model answers or a limit is hit. This is about 150 lines of readable code. LangGraph is an option if the client prefers it, but for three tools and one approval step it adds dependency weight without adding capability. The trade-off is listed in §20.

7.3 Failure handling: no invented results

FailureBackend behaviourWhat the user sees
CRM timeout (connect 3s, read 10s)One retry with backoff (read-only call, safe to retry); then error result to the model with is_error"I couldn't reach the CRM, so I can't confirm this record's details."
CRM 4xx (not found, bad input)No retry; structured error to the model"No record found for that email."
CRM 5xx / rate limitedBackoff retries, then a circuit breaker opens for 60sClear "CRM unavailable" status
LLM API error or timeoutSDK retries; then explicit failure"The assistant is temporarily unavailable."
Model refuses or output is truncatedCheck the stop reason before reading content; treat as failureExplicit failure message, logged

Enforced, not just prompted: the answer schema includes crm_facts_used (which lookup results the answer relies on). If the answer asserts CRM facts but no lookup succeeded in that request, the backend rejects it. The system prompt also says so, but the check doesn't depend on the model behaving.

8. Approval and write path

8.1 Draft state machine

DRAFT ──submit──▶ PENDING_APPROVAL ──approve──▶ APPROVED ──▶ EXECUTING ──▶ SUCCEEDED
                         │                                      │
                         └──reject──▶ REJECTED                  └──▶ FAILED ──retry (same key)──▶ EXECUTING
                                                                └──▶ UNKNOWN ──verify via lookup──▶ SUCCEEDED / FAILED

Every transition is stored in an append-only audit table with actor, timestamp and the exact payload at that moment. Editing a draft after approval resets it to PENDING_APPROVAL.

8.2 Approval

  • The approver sees the final payload exactly as it will be sent: field by field, with the CRM record it attaches to.
  • Approval stores a hash of the approved payload. Execution re-checks the hash, so what is written is exactly what was approved.

8.3 Input validation

  • Pydantic model matching the CRM write endpoint: required fields, lengths, enums, date formats, valid record IDs.
  • The target record is re-checked with a lookup immediately before writing (it might have been deleted or merged since drafting).

8.4 Duplicate prevention

  • Each draft gets an idempotency key when it's created. The actions table has a unique constraint on it, and executing takes a row lock, so two simultaneous approvals or a double click produce one execution.
  • If the CRM API supports idempotency keys, the key is sent with the request. If not, the backend records a marker in the note body or an external-ID field, and on an ambiguous failure (UNKNOWN) searches for that marker before ever retrying the write.
  • A successful action can't be executed again; the endpoint returns the original result.
Rule: a write whose outcome is unknown is never blindly retried. The backend first checks whether it already happened.

9. n8n workflow automation

9.1 One workflow, three branches

Webhook trigger (from backend events)request.classified · action.approved · action.completed / action.failed
↓
Verify signature (HMAC header)
↓
Switch on event type
Routing

By category, notify the right team channel (Slack/Teams/email). Ambiguous requests go to the review channel with a link to the queue.

Approved CRM update

Call POST /actions/{id}/execute on the backend. The backend performs the write with its safeguards and returns the result.

Record outcome

On success or failure, call back /actions/{id}/n8n-result and notify the requester. Failures alert the owner.

9.2 Field mapping

A mapping table (delivered with the workflow export) lists each CRM field, its source (classification output, extracted field, approver input) and its validation rule. Mapping lives in the backend schema, so n8n stays simple and the mapping is testable in code.

9.3 Reliability

  • n8n's error workflow catches failed runs and posts them to an alert channel.
  • Webhook events carry an event ID; the backend and n8n both ignore repeated deliveries.
  • Because the backend is idempotent, n8n retrying a step can't create a duplicate CRM record.

10. LLM provider layer

One small interface with two implementations, selected by configuration. Prompts, schemas and tests are shared, so switching providers is a config change followed by rerunning the evaluation.

14. Logging and token tracking

  • Structured JSON logs with request_id, task, user and timing. Document text, request bodies and CRM data are not logged in full by default; a debug flag enables it in non-production environments.
  • Every LLM call is recorded in llm_calls with token counts from the provider's usage fields, model, latency and stop reason. Estimated cost uses a price table in configuration that the client updates.
  • Usage endpoint and UI page: tokens and estimated cost by day, task (ask/classify/agent) and model.
  • Budget guard: optional daily token ceiling; past it, non-essential tasks return a clear "budget reached" error instead of silently degrading.
  • External calls (CRM, n8n) logged with status, latency and attempt number, so reliability can be measured, not guessed.

15. Security and data handling

  • Secrets (LLM keys, CRM credentials, n8n signing secret) come from environment variables; nothing is committed; logs redact them.
  • Least privilege: the CRM credential used for lookups is read-only where the CRM allows it; the write credential is used only by the execution service, never in the model path.
  • Prompt injection: document chunks, support requests and CRM data are wrapped as untrusted content. The model has no write tool, so an injected instruction can at most produce a draft that a person must approve.
  • Authentication: UI and API protected by the client's existing auth if the template provides it, otherwise simple session auth with roles (user, reviewer, approver).
  • n8n ↔ backend: HMAC-signed webhooks in both directions, with timestamp checks to reject replays.
  • Data sent to LLM providers: only the chunks and request text needed for each call. The client should confirm their provider data-retention settings meet internal policy.

16. Evaluation and testing

This section answers the client's three questions directly: how answer quality, classification and API reliability will be evaluated.

16.1 Answer quality (RAG)

  • Evaluation set: 30–50 questions written from the supplied documents, each with the expected source passage, plus 10–15 questions the documents can't answer, and a few that are answerable only in part.
  • Retrieval hit rate: how often the expected passage is in the top results. This separates search problems from answering problems.
  • Answer correctness: graded against the expected answer (an LLM grader with a fixed rubric, spot-checked by a person).
  • Citation accuracy: do cited passages actually support each claim?
  • Refusal accuracy: on unanswerable questions, the share correctly returned as not_found. This metric matters most for trust.
  • Delivered as a report and a script the client can rerun after changing documents or prompts.

16.2 Classification

  • Split the supplied labeled data into a small example set (used in the prompt) and a held-out test set (never shown to the model).
  • Report accuracy, per-category precision and recall, macro F1, and a confusion matrix showing which categories get confused.
  • Automation trade-off curve: accuracy on auto-routed requests and the share sent to review, at different confidence thresholds. The client picks the threshold.
  • Rerun on each prompt or model change and compare with the previous result.

16.3 API reliability

A fake CRM server (in tests) injects faults on demand. Each scenario is an automated test:

ScenarioExpected result

The same suite runs once against the client's CRM sandbox to confirm the fake behaves like the real API.

16.4 Test layers

  • Unit: chunking, schema validation, state machine, idempotency, routing rules.
  • Integration: API endpoints with a real PostgreSQL (Docker) and recorded LLM responses, so CI is deterministic and free.
  • Evaluation: live-model runs of §16.1 and §16.2, run on demand because they cost tokens.
  • End-to-end: upload → ask → classify → draft → approve → n8n → sandbox CRM record.

20. Assumptions and open questions

Assumptions

  • Documents are text-based (no OCR needed) and total well under a few thousand pages.
  • The CRM sandbox has one read endpoint and one write endpoint as described, with API documentation.
  • The client provides at least ~100 labeled requests (more is better for a meaningful test split).
  • Hosting, LLM usage and n8n hosting costs are paid separately by the client, as stated.
